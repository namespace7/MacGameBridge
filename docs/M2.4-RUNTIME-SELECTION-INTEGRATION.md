# M2.4 — Runtime Selection Integration

## Overview

M2.4 connects three existing pieces into one read-only CLI workflow:

1. **Host capability detection** — identifies the native architecture and
   verifies whether Rosetta 2 x86_64 translation is usable.
2. **Runtime provider discovery** — `RuntimeScanner.scan(paths: .current)`
   finds and validates installed runtimes without executing them.
3. **Runtime selection** — the pure `RuntimeSelector` from M2.3 ranks eligible
   candidates and produces an explainable result.

The selector itself is **not changed** in M2.4. All compatibility and ranking
rules remain in `RuntimeSelector` and `ArchitectureCompatibility`.

## Architecture and data flow

```
                    ┌──────────────────────────────────┐
                    │  HostCapabilitiesDetector        │
                    │  (injectable SystemCommandRunner)│
                    └───────────────┬──────────────────┘
                                    │ HostCapabilities
                                    │  ├─ nativeArchitecture
                                    │  ├─ rosettaStatus / detail
                                    │  └─ selectionRequest
                                    ▼
  RuntimeScanner.scan(paths: .current) ──► RuntimeProviderReport
                                    │
                                    ▼
                     RuntimeSelectionIntegration.makeReport(...)
                                    │
                     RuntimeSelector.select(.automatic, request:)
                                    │
                                    ▼
                     RuntimeSelectionIntegrationReport
                                    │
                    ┌───────────────┴────────────────┐
                    ▼                                ▼
   `runtimes --select` (text)      `runtimes --select --json` (Codable)
```

The integration layer has two entry points:

- `RuntimeSelectionIntegration.makeReport(host:scanReport:)` is pure and is
  used by tests and by callers that already own a scan.
- `RuntimeSelectionIntegration.collect()` is the production path. It detects
  the current host, calls `RuntimeScanner.scan(paths: .current)`, and builds
  the report. Both the detector and the scanner closure are injectable, so
  the production path is independently testable too.

## New CLI commands

```
macgamebridge runtimes --select
macgamebridge runtimes --select --json
```

`--select` takes precedence over `--providers` when both flags are present.
All pre-existing commands (`diagnostics`, `runtimes`, `runtimes --providers`,
`games`, `help`) keep their previous behavior.

### Human-readable output includes

- Host architecture (mapped value plus raw `uname -m` detail).
- Rosetta verification status and explanation.
- A read-only notice: no runtime or game binary was launched.
- Every discovered candidate with ID, provider, status, and architecture.
- The selected runtime (or a clear "no eligible runtime" statement).
- The selector's explanation and any top-level failure.
- A rejection reason for every rejected candidate.
- Safety reminders about validation, installation, and DRM/anti-cheat.

### JSON output

The `--json` variant encodes `RuntimeSelectionIntegrationReport` with:

- `JSONEncoder.outputFormatting = [.prettyPrinted, .sortedKeys]`
- `dateEncodingStrategy = .iso8601`

The report contains the host capabilities, the full provider scan report, the
selector's structured result, and the generation timestamp. It is Codable and
round-trips in tests.

## Host detection behavior

`HostCapabilitiesDetector` uses the same probes historically used by
`Diagnostics`; that probe logic was **moved** into the shared detector and
`Diagnostics.collect()` now calls it, so the two paths cannot drift:

Native architecture is always detected **first**, before any Rosetta probe:

| Fact | Probe | Mapping |
|------|-------|---------|
| Native architecture | `/usr/bin/uname -m` | `arm64`/`aarch64` → `.arm64`; `x86_64`/`x86-64`/`amd64` → `.x8664`; anything else or a failed probe → `.unknown` |
| Rosetta verification (ARM64 only) | `/usr/bin/arch -x86_64 /usr/bin/uname -m` | trimmed output `x86_64` → `verified`; failed probe or unexpected output → `not_verified` |

The translated probe runs **only on a native ARM64 host**. On Intel it can
succeed natively and would be a false Rosetta verification, so it is never
executed there. Unknown native architecture also skips the probe. Both probes
are standard macOS system binaries. No Wine, runtime, or game binary is ever
executed. `SystemCommandExecuting` makes command execution injectable; tests
supply fakes and never depend on the developer's Mac.

## Rosetta verification semantics

| Status | Meaning | `rosettaAvailable` |
|--------|---------|--------------------|
| `verified` | On an ARM64 host, an x86_64 macOS process executed successfully via translation. | `true` |
| `not_verified` | On an ARM64 host, the probe failed or returned an unexpected architecture; on an unknown host, the probe was not attempted. This is **not** proof of absence. | `false` |
| `unavailable` | Rosetta 2 is not applicable on an Intel x86_64 host. The probe is not run there, because it could succeed natively and falsely imply translation. | `false` |

On an Intel Mac the report states
"Rosetta 2 is not applicable on an Intel x86_64 host." and the status is
`unavailable`. On an unknown host architecture the status is `not_verified`
and the probe is skipped — an unknown architecture is never treated as proof
of Rosetta availability.

The selector only receives `rosettaAvailable = true` when the probe positively
succeeded on a native ARM64 host. A `not_verified` result is treated
conservatively: x86_64 runtimes are not assumed to work, but the report says
"not_verified" rather than claiming Rosetta is definitely missing.

`DiagnosticReport.rosetta.status` keeps the same string vocabulary and field
types as before (`verified`, `not_verified`, `unavailable`), and the schema
version remains `1.0`.

## Selection behavior and limitations

- Selection policy is always `.automatic` in the CLI workflow; it uses the
  existing deterministic ranking (status, architecture, provider, ID).
- Only installations with `status == .validated` are eligible.
- Unknown host architecture rejects every candidate.
- Rosetta is never assumed: x86_64 candidates on ARM64 require a `verified`
  probe.
- The selector does not prove game compatibility or successful launch. It
  only evaluates host architecture compatibility and structural validation.
- The integration service does not add or duplicate any selection logic.

### What `validated` means — and what it does not

In M2.2/M2.3, `validated` means the discovery scan found the runtime's Wine
executable, confirmed the executable bit, and read its Mach-O architecture
from file metadata (via `/usr/bin/file`). It is a structural check only.

`validated` does **not** mean:
- the runtime was launched,
- a game was launched or played,
- a specific game's offline or online mode works,
- DRM, licensing, or anti-cheat was tested or bypassed,
- a GPU/graphics backend was exercised.

Any compatibility claim still requires a reproducible test record with the
runtime version, macOS build, graphics backend, game edition, and evidence.

## Read-only safety guarantees

- No installer, runtime, or game binary is launched by discovery, validation,
  host probing, selection, or any M2.4 command.
- No macOS settings, runtime installations, bottles, prefixes, or game files
  are modified.
- Network downloads are not performed; no third-party dependencies are added.
- The translated Rosetta probe executes only `/usr/bin/uname`, a standard
  macOS system binary, to check whether x86_64 translation works.
