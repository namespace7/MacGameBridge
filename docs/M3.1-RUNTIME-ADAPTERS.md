# M3.1 — Runtime adapter architecture and exact runtime pinning

## Goal

Give runtime-specific behaviour a provider-independent home, and let users
record an *exact* already-discovered runtime installation for an environment
without ever choosing a substitute. This milestone changes metadata only.

No runtime binary is executed, no prefix is created, deleted, or initialized,
no software is installed or downloaded, no game is launched, and no macOS
security setting is changed. An environment stays `planned` and is never marked
`provisioned`.

## Adapter contract

`RuntimeAdapter` (`Sources/MacGameBridgeCore/Runtime/RuntimeAdapter.swift`) exposes:

| Member | Purpose |
|---|---|
| `providerID` | The `RuntimeProviderID` this adapter supports. |
| `capabilities` | What the adapter can do. M3.1 adapters report read-only validation and exact pinning; `provisioning` and `launchConfiguration` are always `false`. |
| `validate(_:host:)` | Read-only validation of one `ProviderInstallation` against injected `HostCapabilities`. |

Structured results and errors:

- `RuntimeAdapterValidationResult`: provider ID, installation ID, eligibility,
  architecture, typed `RuntimeAdapterValidationIssue` values, and the structured
  `RuntimeSelectionRejection` produced by architecture compatibility checks.
- `RuntimeAdapterError`: explicit `.unsupportedProvider(_)` and
  `.providerMismatch(expected:actual:)` cases.

Validation uses metadata that `RuntimeScanner` already discovered. It does not
re-run `/usr/bin/file` and never launches the executable. A path that does not
exist can still be validated as a fixture because the adapter does no file I/O.

### Supported providers

| Provider | Adapter | Pinning |
|---|---|---|
| `.wine` (standalone Wine) | `WineRuntimeAdapter` | Yes |
| `.crossover` | none | Explicit unsupported-provider error |
| `.whisky` | none | Explicit unsupported-provider error |
| `.sikarugir` | none | Explicit unsupported-provider error |

Discovery of a wrapper runtime is unchanged and still reported by
`runtimes --providers`. Discovery support is **not** adapter support.

`RuntimeAdapterRegistry` resolves adapters by provider ID. It has a default
registry containing only `WineRuntimeAdapter`, and it is injectable in the CLI
and pinning service. Adding a CrossOver, Whisky, or Sikarugir adapter later does
not require changes to the CLI parser or environment commands.

`WineRuntimeAdapter` accepts only the standalone shape: no app bundle, an
absolute local Wine executable path, status `validated`, a known architecture,
and architecture compatibility with the injected host. A `.wine` installation
with a bundle URL is rejected as an unsupported installation shape.

## Exact pinning semantics

`macgamebridge environments pin-runtime <environment-id> --runtime <installation-id> [--replace] [--json]`

- `--runtime` must equal a literal, already-discovered `ProviderInstallation.id`
  shown by `runtimes --providers` (or in the selection report). No prefix
  matching, fuzzy lookup, ranking, or "best available" fallback is performed.
- If the ID is absent from the injected installations, pinning fails. Other
  validated installations are never substituted.
- If two discovered installations share the same ID, pinning fails as ambiguous.
- The installation provider must have a registered adapter; unvalidated,
  unknown-architecture, malformed, and host-incompatible installations are
  rejected. x86_64 runtimes on Apple Silicon require positively verified
  Rosetta facts; a failed probe is never treated as availability.
- Pinning an environment that already has a *different* pin requires explicit
  `--replace`. Re-pinning the same ID is not a replacement.
- The exact-installation policy from the M2.3 selector is reused with
  `allowFallback: false`. Host facts and the architecture compatibility helper
  are injected; the service never calls live system probes.

`macgamebridge environments unpin-runtime <environment-id> [--json]`

- Removes only the pin. ID, game profile, display name, prefix URL, creation
  timestamp, lifecycle state, and all other fields are preserved.
- Pinning and unpinning both update `updatedAt` from the injected clock.

## Persistence safety

`EnvironmentRepository.updateRuntimeInstallationID(for:runtimeInstallationID:updatedAt:)`:

- reads and writes under the repository's existing lock and uses its atomic
  file write;
- requires the stored record to equal the caller's read record, rejecting a
  stale update instead of overwriting a concurrent change;
- re-applies duplicate-ID and duplicate-game-prefix checks before writing;
- copies identity, game profile, name, prefix URL, lifecycle state, and creation
  timestamp from the stored record, so only the pin and update timestamp can
  change;
- leaves the registry file byte-identical on every rejected update.

The JSON schema remains `1.0`; the environment object shape is unchanged.
`pin-runtime --json` and `unpin-runtime --json` emit a single `GameEnvironment`,
matching `show --json` and `create --json`. Existing `diagnostics`, `runtimes`,
`games`, and prior `environments` JSON contracts are unchanged. The human-readable
provider and discovery output now also prints the exact ID for copy/paste.

Public API additions are `RuntimeAdapter` and its supporting types,
`WineRuntimeAdapter`, `RuntimeAdapterRegistry`, `RuntimePinningService` and its
dependencies/errors, the conditional repository update method, new
`EnvironmentCommand` cases, and additive error cases on `EnvironmentCLIError`
and `EnvironmentRepositoryError`. `EnvironmentCLIServices.init` gained only
trailing parameters with defaults, so existing call sites compile unchanged.
Clients with exhaustive switches over those public enums need new cases.

## Dependency injection

`EnvironmentCLIServices` and `RuntimePinningDependencies` inject:

- runtime installations;
- host capability facts (`HostCapabilities`);
- adapter registry;
- time provider;
- environment repository / storage URL;
- game profile loader and prefix validator (existing M3 seams).

All tests use temporary directories and fixture installations. They never depend
on Wine, CrossOver, Whisky, or Sikarugir being installed, and never execute a
runtime or game binary.

## CLI usage

```bash
# Print exact installation IDs.
macgamebridge runtimes --providers
macgamebridge runtimes --select

macgamebridge environments pin-runtime env-1 --runtime 'wine:/opt/homebrew/Cellar/wine/10.0/bin/wine64'
macgamebridge environments pin-runtime env-1 --runtime 'wine:/other/wine64' --replace
macgamebridge environments unpin-runtime env-1

# Machine-readable results.
macgamebridge environments pin-runtime env-1 --runtime 'wine:/...' --json
macgamebridge environments unpin-runtime env-1 --json
```

Exit codes follow the existing `environments` convention: `2` for argument
errors and `1` for operational failures. Every failure leaves the registry
unchanged.

## Known limitations

- Only standalone Wine has an adapter. Wrapper providers are discovery-only.
- A pinned runtime is a metadata reference, not provisioning evidence. There is
  no launch path, prefix initialization, graphics-backend configuration, or
  compatibility claim in this milestone.
- Installation IDs are derived from discovered paths. Reinstalling or moving a
  runtime can invalidate a pin; use `runtimes --providers` to obtain a fresh ID.
- Validation relies on the status and architecture recorded by the last
  read-only scan; it does not rescan or re-execute metadata tools.
- Atomic writes and in-process locking prevent partial files and in-process
  races. There is still no cross-process file lock.
- Adapter capabilities for provisioning and launch configuration are modelled
  but unimplemented and always reported as `false`.
- No DRM, anti-cheat, or publisher security control is bypassed.
